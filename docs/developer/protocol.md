# Wire protocol

`gpudog` and `gpudogd` talk over a `SOCK_STREAM` Unix domain socket using a
small binary protocol. The current version is **7**. The definitions are in
`crates/gpudog-core/src/protocol/mod.rs`.

This page is for people writing another client or changing the protocol.
Version 7 deliberately rejects older peers. Historical v3 to v6 fixtures
remain for reference; current v7 fixtures are independently generated by
`scripts/gen-golden-v7.py` in this repository.

## Framing

All integers are little-endian.

```text
[u32 body_size][u16 message_type][payload...]
               \________ body_size bytes ________/
```

`body_size` counts the type and the payload. It must not exceed 65,536
(64 KiB). A larger value is rejected before any buffer is allocated.

### Common encodings

| Name | Encoding |
| -- | -- |
| `string` | `u32 length`, then `length` bytes. At most 4,096 bytes. |
| `gpu_list` | `u32 count`, then `count` × `u32 index`. At most 1,024 entries, each index below 1,024, no duplicates. |
| `uuid_list` | `u32 count`, then `count` × `string`. At most 1,024 entries. Each is `GPU-` (any case) followed by ASCII letters, digits and `-`, at most 96 bytes. No duplicates, compared case-insensitively. |
| `bool` | `u8`, `0` or `1`. |
| `Option<u32>` / `Option<u64>` | `bool present`, then the integer only when present. `None` differs from `Some(0)`. |

All bools, including option presence flags and `truncated`, reject values
other than `0` and `1`.

## Message types

| Value | Name | Direction | Payload |
| -- | -- | -- | -- |
| 1 | `hello` | client → daemon | `u32 version` |
| 2 | `hello_ack` | daemon → client | `u32 version` |
| 3 | `acquire` | client → daemon | see below |
| 4 | `queued` | daemon → client | `u32 position` |
| 5 | `granted` | daemon → client | `gpu_list gpus` (never empty), `uuid_list uuids` (same length; `uuids[i]` names `gpus[i]`), `u64 hold_limit_ms` (see below) |
| 6 | `denied` | daemon → client | `u16 reason`, `string detail` |
| 7 | `ping` | client → daemon | empty |
| 8 | `pong` | daemon → client | empty |
| 9 | `status` | client → daemon | empty |
| 10 | `status_reply` | daemon → client | see below |

### `acquire`

| Field | Type | Meaning |
| -- | -- | -- |
| `selection` | `u8` | `0` = count from UUID candidates; `2` = explicit UUIDs. `1` is reserved and rejected. |
| `num_gpus` | `u32` | `1` to `1024`. With `selection = 2`, must equal `uuids` length. |
| `gpus` | `gpu_list` | Reserved; must be empty in every request. |
| `uuids` | `uuid_list` | Empty unless `selection = 2`. |
| `candidates` | `uuid_list` | Mandatory non-empty with `selection = 0`; empty otherwise. The client's visible UUIDs, intersected with managed devices. Too few managed candidates is `unsatisfiable`. |
| `timeout_ms` | `u64` | `0` = wait forever. At most `0xFFFFFFFF` (about 49.7 days). |
| `command` | `string` | Display text for logs and the dashboard, at most 256 bytes; longer is a protocol error. Not verified. |

### `granted`

`hold_limit_ms` is how long, in milliseconds from the grant, the client may
hold the GPUs: the daemon's `max_hold_ms` at the time of the grant. `0`
means no limit, and the value is at most `0xFFFFFFFF`. The client is
expected to stop its command when the limit ends. The daemon never revokes
the reservation: it holds the GPUs until the connection closes, and logs
once that the limit has passed.

### `status_reply`

| Field | Type |
| -- | -- |
| `device_count` | `u32`; informational total, not capped by the list/index bounds |
| `devices` | `u32 count`, then per device: `u32 index`, `string name`, `string uuid` |
| `holders` | `u32 count`, then `reservation` entries |
| `waiting` | `u32 count`, then `reservation` entries |
| `truncated` | `bool` |
| `observing` | `bool` |
| `watch_unmanaged_ms` | `u64`; when observing, must be `1..=3_600_000` |
| `allocation_paused` | `bool` |
| `observation_age_ms` | `Option<u64>` |
| `observation_error` | `string`, at most 256 bytes |
| `busy_gpus` | `gpu_list` |
| `processes` | `u32 count`, then `gpu_process` entries |

Device, holder, waiting and process lists each hold at most 256 entries.
`busy_gpus` uses the common GPU-list bound. `truncated` reports shortened
lists. Every process GPU and busy GPU must be below both 1,024 and
`device_count`; this does not require the device to appear in a shortened
`devices` list. Process rows may repeat a GPU (or a PID on multiple GPUs).

The appended observation fields describe a daemon snapshot, not a client
query. `observing = false` with `watch_unmanaged_ms = 0`, no observation age,
and empty observation lists/error is the default and is valid. The wire does
not enforce relationships between pause, age, error and process contents;
these are reported state, not allocation authorisation inputs.

A `gpu_process` entry is encoded in this order:

| Field | Type | Meaning |
| -- | -- | -- |
| `gpu` | `u32` | Daemon logical GPU index |
| `pid` | `u32` | Observed PID in the daemon's namespace |
| `uid` | `Option<u32>` | Process UID, if available |
| `start_time` | `Option<u64>` | Linux procfs process start time in clock ticks since boot, if available |
| `used_memory` | `Option<u64>` | GPU memory in bytes, if available |
| `ownership` | `u8` | `0` = managed, `1` = managed (wrong GPU), `2` = not managed, `3` = unknown; other values rejected |
| `command` | `string` | Advisory display text, at most 256 bytes |

Unavailable optional process metadata remains absent rather than becoming
zero. Commands and observation errors are byte strings and untrusted text;
clients must sanitise them before rendering.

A `reservation` entry is:

| Field | Type | Meaning |
| -- | -- | -- |
| `id` | `u64` | Opaque, stable for the life of the reservation |
| `uid` | `u32` | Owner, from `SO_PEERCRED` |
| `pid` | `i32` | Client PID as seen through the daemon's peer credentials; may be `0` across PID namespaces |
| `gpus` | `gpu_list` | GPUs held; empty while waiting |
| `num_gpus` | `u32` | GPUs wanted |
| `age_ms` | `u64` | Time since the grant, or since the request was queued |
| `hold_limit_ms` | `u64` | The holder's `granted.hold_limit_ms`; `0` for no limit, and always `0` while waiting. At most `0xFFFFFFFF`. |
| `position` | `u32` | Position in the daemon's service order, starting at `0`; always `0` for holders. The daemon orders by load, so it can change. |
| `command` | `string` | Client-reported command line, sanitised to printable ASCII |

### Deny reasons

| Value | Name | Client message |
| -- | -- | -- |
| 0 | `unspecified` | request refused |
| 1 | `version_mismatch` | protocol version mismatch |
| 2 | `timed_out` | timed out waiting for GPUs |
| 3 | `invalid_request` | invalid request |
| 4 | `unsatisfiable` | request can never be satisfied |
| 5 | `shutting_down` | the daemon is shutting down (reserved; not sent today) |
| 6 | `internal_error` | the daemon reported an internal error |

Clients must accept unknown reason values and show the `detail` string.

## Session

```text
client                              daemon
  connect -------------------------->
  hello{version} ------------------->
         <------------------------- hello_ack{version}  or  denied{version_mismatch}
  ping / status (any number) ------->
         <------------------------- pong / status_reply
  acquire{...} --------------------->
         <------------------------- queued{position}    (at most once)
         <------------------------- granted{gpus}       or  denied{...}
  [ run the command, keep the socket open ]
  close ---------------------------->  reservation released
```

*   The first message must be `hello`.
*   After the handshake the client may send `ping` and `status` any number of
    times. Each `acquire` ends this phase; one connection holds at most one
    reservation.
*   Each message before the reservation is granted or queued must arrive
    within `handshake_timeout_ms`, or the daemon closes the connection.
*   Any other message, or a malformed frame, makes the daemon close the
    connection.
*   Closing the connection, at any point, cancels the request or releases the
    GPUs.

## Compatibility rules

Before 1.0 there is no promise of compatibility between releases (see
[Compatibility between versions](../installation.md#compatibility-between-versions)):
a release may increase the protocol version, and `CHANGELOG.md` says when
it does. The rules below say what such a change must do.

*   Adding a new message type is backward compatible. Older peers reject it as
    an unknown type.
*   Changing the layout of an existing message, or the number of an existing
    type or reason, is a breaking change and requires increasing the protocol
    version.
*   The daemon refuses clients with a different version at the handshake.
*   Version 2 added `acquire.command` and the `status`/`status_reply` pair.
*   Version 3 added `granted.uuids`, `acquire.uuids`, `acquire.candidates`
    and `selection = 2`.
*   Version 4 requires UUID-only request selection and non-empty count
    candidates. Field layout is unchanged, but these semantics are breaking;
    older peers must not interpret local indices or empty visibility as
    unrestricted allocation.
*   Version 5 appends the observation state and GPU process rows to
    `status_reply`, and requires canonical bool and option flags. All other
    payload layouts and message-type values remain unchanged. Client and
    daemon must both use v5; v4 status payloads are incomplete v5 messages,
    not snapshots with implicitly disabled observation.
*   Version 6 removes the `i32 priority` from `acquire` and from each
    `reservation` entry. The daemon orders its queue itself, by how many GPUs
    each user already uses; see
    [Scheduling policy](architecture.md#scheduling-policy).
*   Version 7 appends `u64 hold_limit_ms` to `granted` and inserts one after
    `age_ms` in each `reservation` entry.

## Device identity

Indices in grants/status are the daemon's logical display metadata. Requests
identify GPUs by UUID only. A client must resolve its local CUDA indices and
enumerate its visibility before sending. Empty count candidates and legacy
numeric selections are invalid messages, not requests for any managed GPU.

The client must put `granted.uuids`, never `granted.gpus`, into
`CUDA_VISIBLE_DEVICES`. A UUID names the same GPU in every container and on
the host. The daemon resolves `selection = 2` against its own list and
answers `invalid_request` with `<uuid> is not managed by this daemon`
when a UUID is not one of its devices.
